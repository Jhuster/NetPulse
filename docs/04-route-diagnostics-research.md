# 路径诊断：Traceroute / MTR 研究与设计建议

研究日期：2026-10-29。状态：功能建议与交互草案，未接入应用。

## 结论

建议在 NetPulse 中新增一个“路径诊断”入口，提供“快速查看路径”和“持续观察”两种任务。前者使用 traceroute 得到路径快照，后者采用 MTR 的逐 TTL 持续采样机制。先做快速路径及可复用的数据模型，再做持续观察与时间关联；地图后置。

最有价值的差异是：先展示目标表现，再解释中间跳的可观测性，最后才给出有条件的异常线索。不能把每个未回复的路由器都标成网络故障，也不能承诺准确定位故障设备。

本文基于官方产品说明、手册、开源项目资料与本机回环验证。未安装运行 BestTrace、PingPlotter、NextTrace 或 MTR，竞品描述不等于完整体验报告。交互演示使用明确标注的虚构数据。

## 2. 用户任务与首屏

用户需要回答三个问题：目标是否出现探测异常？异常从什么时候开始？路径上的哪些观测值得进一步检查？

主导航建议为“质量监测 / 路径诊断”，不让用户先判断陌生的命令名字。路径页输入目标后选择：

- **快速查看**：一次路径扫描，展示已观察到的 TTL、地址和 RTT 样本；默认每 TTL 三个探测，只展示回复数，不用三包推断长期丢包率。
- **持续观察（MTR）**：针对同一目标逐 TTL 持续采样；建议默认观察两分钟，可提前停止或继续。参数属于设计起点，需用真实性能验证调整。

首屏从上到下：

1. 目标、固定解析 IP、协议/端口、统计时段、测试状态。高级参数折叠。
2. 目标探测结果：回复/发送、未响应比例、RTT、有效样本数；没测到目标时显示“未收到目标回复”，不默认宣布服务器宕机。
3. 一句证据摘要，例如“目标本次全部回复；第 3 跳存在未响应，但后续跳未观察到同样现象”。
4. 逐跳表格。默认选中目标行；默认按 TTL 排序，不能按 RTT 排序后仍画成一条路径。
5. 选中跳与目标的同时间轴对照，以及“查看依据/原始记录”。

推荐“概览优先”布局。另提供“表格优先”的紧凑布局作为专业视图候选，不强迫普通用户看齐全部统计列。

## 3. 默认展示哪些统计

| 字段 | 命名与行为 |
| --- | --- |
| 跳数 | TTL，不宣称等于实际物理路由器数量 |
| 节点 | IP；ASN/运营商与大致地域作为补充，未知显示未知 |
| 探测未响应 | `未回复数 / 已到期限探测数`，附比例；中间跳不命名为“转发丢包” |
| RTT | 成功回复的平均往返时延；点开看 min、P95、max、有效样本数 |
| 波动 | 默认用小型趋势线，详细面板才展示 jitter/标准差，并写明口径 |
| 观察 | “未回复”“多地址”“样本不足”“目标回复”等事实标签；推断单独标明 |

待回复请求不进未响应分母；启动失败和权限错误单列；无成功样本 RTT 留空。快速扫描展示“回复 2/3”，不依此给节点长期健康评级。持续观察建议以最近 60 秒为默认统计窗，另可切累计；所有行使用同一时段但保留各自实际分母。样本量不足只提示“继续采样”，不能编造置信度百分比。P95 与 jitter 的样本量、算法和未回复筛除必须可查看。

## 4. 必须避免的误读

### 中间跳不回复不等于转发丢包

路由器可能对 ICMP 错误报文限速或不回复；这并不直接表示经过它的业务流量丢失。MTR 官方 README 有明确说明，[RFC 1812 §4.3.2.8](https://www.rfc-editor.org/rfc/rfc1812.html#section-4.3.2.8) 也说明 ICMP 错误的限速机制。[PingPlotter 官方解释](https://www.pingman.com/kb/24) 强调应先检查最终目标与后续跳的表现。

例如第 3 跳 80% 未响应，后续跳与目标 0% 未响应：中间行使用灰色“回复受限或未响应”，摘要仅说明没有观察到下游共同异常，不能确定“此路由器一定限速”，也不能保证业务正常。

### 后续同时异常也只是线索

第 4 跳之后与目标同时出现未响应，可以描述为“异常首次在第 4 跳附近被观察到”。逐跳探测是不同报文，并非追踪同一个业务包，回程也可能不同；缺少双向、跨源或业务证据时，不输出“第 4 跳就是故障点”“某运营商导致丢包”。

若目标本身不回复，可能是目标/端口策略、路径或回程问题，结果应为“当前协议下无法确认”，建议独立进行另一种协议或业务端口测试。

### 相邻 RTT 差不能当作链路单向时延

每行测量的是本机到该回复节点再返回的 RTT。相邻行相减可能为负，也不代表那条物理链路耗时。UI 不画“这段线增加了 30 ms”的确定结论。原理边界见 [RFC 2681](https://www.rfc-editor.org/rfc/rfc2681.html)。

### 多地址不一定是路由切换

负载均衡可能让同一 TTL 出现多个回复地址，传统 traceroute 还可能拼接出并不存在的链路。[Paris Traceroute 研究](https://paris-traceroute.net/) 解释了相关测量伪影。

默认在一个 TTL 行中展开多个观察地址，不连成确定的完整分叉拓扑。首次标记“观察地址变化”；只有在固定目标 IP、协议、探测参数及流标识条件下，经重复观测才生成候选路径变化事件。记录观测路径版本，不能把最新 IP 与整个会话历史统计拼在一起。

### 地图与网络归属不能过度解读

地图只表示 IP 库估计地点之间的示意连接，不代表真实光纤、机房、海缆或业务绕行证明。ASN/地域查询独立异步进行，失败不阻断核心探测；显示来源与查询时间。初版建议先不引入外部地理查询，避免把核心可用性绑定到在线服务。

## 5. 可理解的状态与交互

- 测试中：“正在探测第 N 跳，已有 M 个 TTL 收到回复”；最大 TTL 是上限，不是已知总进度，不显示虚假百分比。
- 结束状态区分：收到目标回复、达到跳数上限、达到时间预算、用户停止、权限/进程错误。到达判定必须按探测协议和响应类型/码实现，不能仅凭回复 IP 等于目标就判定到达；TCP 端口回应也不代表业务请求成功。
- `*` 替换为“本跳未回复”，并可查看原因边界；后续 TTL 继续探测，不能仅因一个中间跳静默终止。
- 结果默认显示目标表现；异常红色只用于已观察到的目标探测异常。中间未响应使用灰色；证据不足给文字提示。
- 点击行选择节点，固定目标作为对照；点击时间段时，摘要、表格、曲线与路径版本同步切换。
- 默认锁定会话目标解析 IP，DNS 地址变化形成新分段；不能将旧地址和新地址混算。
- 协议/端口变化新建探测分段，明显展示实际协议；不静默切换 ICMP、UDP、TCP 后混算。
- 移动端用逐跳列表和详情抽屉替代横向宽表，统一日志与数据语义，不承诺沿用桌面命令。

## 6. 实现路径与本机验证

本机存在 `/usr/sbin/traceroute`，当前 PATH 未发现 `mtr`。系统 traceroute 手册支持 `-n`、`-q`、`-w`、`-m`，以及 ICMP/UDP/TCP 选项；默认出站探测为 UDP，不能把所有平台默认协议写成相同值。

2026-10-29 验证命令：

```sh
/usr/sbin/traceroute -n -m 2 -q 1 -w 1 127.0.0.1
```

在任务沙箱内执行被阻止；获准在任务沙箱外、以当前用户运行后成功，输出一跳 `127.0.0.1 3.093 ms`。这是回环与命令可执行性验证，不等于公网成功、App Sandbox 可用或移动端可用。未安装依赖、未更改系统权限、未对公网进行 traceroute。

建议适配器边界为 `start / probe / hop-observation / path-snapshot / stop / error`，应用层负责统一窗口与回放：

| 路径 | 用途 | 限制与下一步 |
| --- | --- | --- |
| 系统 traceroute 适配 | 第一阶段快速路径，减少依赖 | 在真正 .app 中验证权限、输出、取消与超时；解析按平台实现 |
| 官方 MTR 子进程 | 候选持续采集引擎，读取事件流而非屏幕 ANSI 表格 | 本机未安装；需验证辅助进程权限、取消、事件完整性及打包。官方仓库标示 GPL-2.0，发行前评估分发义务 |
| NextTrace 子进程 | 另一候选，当前文档提供持续 MTR 与机器事件接口 | 功能与部署范围需固定具体版本再验证；官方仓库标示 GPL-3.0。协议、平台能力不能只凭编译成功判断 |
| 自研逐 TTL 引擎 | 更细控制与平台适配 | 探针关联、ICMP 引用包解析、多路径、权限与维护成本更高，暂不作为第一阶段前提 |

MTR 的逐跳持续测量，必须仍然向最终目标发送带不同 TTL 的探针。不能先 traceroute 得到一组路由器 IP，再分别 Ping 这些 IP 就宣称实现了 MTR；后者路径和目标回应策略可能不同。

MTR 的辅助进程权限设计应参考 [官方 SECURITY](https://github.com/traviscross/mtr/blob/master/SECURITY)，不将整套 UI 以管理员身份运行。未来 Windows、Android、iOS 先做能力探针与限制矩阵，当前只承诺统一模型和展示思路。

## 7. 采样预算、日志与验收

建议初始参数：快速查看最多 30 TTL、每 TTL 3 个样本、每包等待 1 秒、总时限可配置，默认总预算 60 秒；超预算返回部分结果，不承诺每次扫描完整。持续观察默认两分钟，每 TTL 目标间隔 2 秒，另有全局发包上限（候选 10 包/秒）和在途上限；实际 TTL 较多时降低每 TTL 频率，UI 报实际样本数。上述参数为产品建议，尚未压测确认。

终点 Ping 和路径诊断要记录各自协议与测量来源。不同协议的结果可以并排呈现，不能合并分母，也不能据其相关性直接断定故障。

延续 CSV + 文本诊断：

- `trace_probes.csv`：探针时间、ID、TTL、最终目标 IP、协议/端口、结果、回复 IP、RTT、ICMP 类型/码、观测分段、流参数标识。
- `trace_windows.csv`：窗口时间、观测分段、TTL、发送/已到期/回复/超时/错误数、RTT 统计、统计状态。TTL 聚合分母覆盖该 TTL 的探针；按回复 IP 的子统计只展示回复分布，不能把未知超时任意分摊给某个 IP。
- `trace_events.csv`：地址集合变化、目标解析变化、暂停/恢复、协议变更、部分结果等事件；字段清晰、缺失留空。
- `diagnostics.txt`：原始输出与引擎信息。元信息增加引擎版本、有效参数和 IP 归属来源。

新文件独立于现有 Ping CSV，不给旧格式强塞路由字段。导入后不重新做 DNS、GeoIP 或网络探测，按记录恢复当时结果。

建议分三步交付：

1. **快速路径**：渐进结果、目标状态、TTL 多地址、原始输出、导出/回放；不做自动故障点判断。
2. **持续观察**：逐 TTL 采样、统一时间窗、目标对照、历史路径分段、证据提示。
3. **增强解释**：可选 ASN/地域、协议对照、路径差异、移动端布局；地图视实际价值决定。

首批验收场景必须包含：中间静默但目标回复；中间高未响应而后续正常；目标不回复但 TCP 端口可响应；后续共同异常；同 TTL 多地址；目标 DNS 地址变化；部分结果；权限失败；取消和退出；日志回放不联网。

## 8. 建议本轮 review 的重点

先确认“目标结果优先 + 跳表 + 时间联动”的主布局，以及是否将快速路径作为下一次可交付增量。持续 MTR 与地图不必绑定同一版本上线。研究文件与演示不修改现有应用的采集行为。

交互草案检查：已在浏览器验证三种合成场景、节点选择与布局切换，且通过 JavaScript 语法检查。该验证仅针对演示，不代表路径采集功能已实现。

## 9. 表格优先布局补充：网关、地域与状态

按本轮反馈，交互草案默认采用“表格优先”，补充：

- **出口网关**：节点旁显示标签，顶部显示出口网关地址。正式实现应从当前目标有效路由/接口信息识别，再与路径观测匹配；不能因为 TTL=1 就无条件标为网关。VPN、隧道、直连目标或无可见网关时单独说明。本轮演示网关为设定值。
- **国家 / 省份**：与 IP 同一单元格分行展示，作为补充信息；私网/共享地址不做公网地理推断。未知国家、省份显示未知；不适用显示不适用。归属来源与查询时间放在详情，查询失败不阻断探测。本轮地理信息为合成演示，没有调用地理服务。
- **状态**：单独一列，使用颜色和文字共同说明。绿色为“未见探测异常”；红色为“目标探测异常”或“探测异常，待核查”；橙色为地址变化等需检查的事件；灰色为未回复、可能回复受限或证据不足。红色不等于已定位转发故障设备。
- **中间跳误报控制**：中间跳未响应较高但下游回复正常，保持灰色说明；与目标在同一时间段出现共同异常时，可以标红作为核查线索，不能据此判定责任。RTT 的好坏应结合业务要求与稳定基线，不设置适用于所有地区的单一阈值。

演示提供有红色异常的场景，仍可切换到中间回复受限和地址变化场景检查区别，并保留用户已有场景选择。正式功能尚未实现。
